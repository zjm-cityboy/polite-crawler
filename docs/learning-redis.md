# Redis 学习文档（对照本项目实战）

> 定位：看完这份文档，你能讲清楚"这个爬虫项目里 Redis 到底干了什么、为什么是它"。

## 一、Redis 是什么（一句话 + 比喻）

**Redis = 一个把数据全部放在内存里的超快键值数据库。**

比喻：PostgreSQL 是档案柜（数据在磁盘上，翻找慢一点，但永久保存）；
Redis 是你桌上的便签本（数据在内存里，摸一眼就到手，但桌子一收拾可能就没了）。

"快"到什么程度：内存读写在 **0.1 毫秒级**，PG 磁盘查询在 **几毫秒级**——差一个数量级。

## 二、为什么这个项目需要它（没有会怎样）

爬虫每发出一个请求前都要问一个问题：**"这个 URL 我爬过吗？"**

- 用 PG 去查：每个请求多花几毫秒，而且海量去重查询会和文章入库的写入抢锁、互相拖慢；
- 用内存里的 Python `set()`：进程一重启全忘光，断点续爬失效；开两个爬虫进程时，各记各的账，互相不知道对方爬过什么。

Redis 两个问题全解决：**内存速度 + 独立进程**（重启爬虫不丢指纹，多个爬虫共享同一份账本——后者就是"分布式去重"的雏形）。

**分工表（面试高频）**：

| | Redis | PostgreSQL |
|---|---|---|
| 角色 | 便签本：去重指纹 | 档案柜：文章数据 |
| 存什么 | 40 位 SHA1 哈希（几百字节） | 完整正文（大文本） |
| 读写模式 | 每请求 1 次（高频小读写） | 每文章 1 次（低频大写入） |
| 丢了的后果 | 只是可能重复爬一遍（PG 的 UNIQUE 约束还会兜底） | 数据永久丢失 |

> 为什么文章数据不也放 Redis：内存贵、放不下太多；Redis 的价值在"快"，不在"可靠存大件"。

## 三、核心概念（最小必要知识）

### 1. 键值数据库
所有数据长成 `键 → 值` 的形式，像字典：`dupefilter:urls → {指纹1, 指纹2, ...}`。
键名用冒号分层是社区惯例：`业务域:对象`（本项目就是 `dupefilter:urls` 和 `dupefilter:content`）。

### 2. 五大基础数据结构（本项目只用到 SET）

| 结构 | 比喻 | 本项目用了吗 |
|---|---|---|
| String | 一个变量 | - |
| **SET（集合）** | 一袋不重复的球 | ✅ 两处去重全靠它 |
| LIST | 排队的一列人（可两头进出） | -（队列场景用它，见学习文档末尾延伸） |
| HASH | 一个对象（字段→值） | - |
| ZSET | 带分数的排行榜 | - |

### 3. SADD：一条命令完成"查 + 记"（本项目最核心的一行）

```
SADD dupefilter:urls <指纹>
返回 1 → 集合里原本没有，是新的（放行请求）
返回 0 → 集合里已经有了，重复的（丢弃请求）
```

关键性质：**原子操作**——"检查是否存在"和"添加进去"一步完成，两个爬虫进程同时 SADD 同一个指纹也不会出乱子（不会有"都查到不存在、都放行"的竞态窗口）。

### 4. 亲自上手看一眼（项目环境里直接敲）

```bash
docker exec -it crawler-redis redis-cli     # 进 Redis 命令行

SCARD dupefilter:urls      # 数一数已登记多少个 URL 指纹（SCARD = 集合大小）
SCARD dupefilter:content   # 正文指纹数
SMEMBERS dupefilter:urls   # 列出全部指纹（多了会刷屏，看看就好）
DEL dupefilter:urls        # 清空 URL 账本（下次运行会重新爬全部种子）
```

## 四、本项目里的两处 Redis（代码对照）

### 用法 1：请求级去重 —— `news_crawler/dupefilter.py`

把 Scrapy 默认的"内存去重过滤器"换成 Redis 版（类名 `RedisDupeFilter`）：

```python
def request_seen(self, request):
    return self.redis.sadd(self.key, url_fingerprint(request.url)) == 0
    #                    返回 1（新的）→ == 0 为 False → 不算"见过" → 放行
    #                    返回 0（旧的）→ == 0 为 True  → 算"见过"  → 丢弃
```

这一招的学名：**手写实现了 scrapy-redis 库的核心思想**（面试可以直说：我没直接装 scrapy-redis，而是把它的核心 60 行手写了一遍，为了吃透原理）。

### 用法 2：内容级去重 —— `news_crawler/pipelines.py` 的 `RedisDedupePipeline`

同一个键位思想换了维度：URL 指纹管"链接爬没爬过"，**正文指纹管"文章存没存过"**——
同一篇报道被两个栏目转载（URL 不同、正文相同），第二份直接拦截。

### 双保险结构

```
请求级（dupefilter:urls）   →  挡住"爬过的链接"
内容级（dupefilter:content） →  挡住"换链接的重复文章"
PG UNIQUE(content_fp)       →  Redis 全丢了的最后兜底
```

## 五、踩坑实录（本项目真实发生）

1. **去重指纹会"记住"失败的运行**：调试期间管道报错、数据没入库，但 URL 指纹已登记 —— 重跑时全部被过滤，看起来"爬虫坏了"。处理：`DEL dupefilter:urls` 清账重来。（这其实证明去重在工作，语义没错。）
2. 容器内 Redis 没设密码：学习环境可接受，生产必须 `requirepass`。

## 六、面试怎么答

**Q：为什么去重用 Redis 不用 MySQL/PG？**
要点：①去重检查发生在每个请求前，是高频小查询，内存级的 Redis 快一个数量级；②独立进程存储，爬虫重启不丢、多进程共享，天然支持断点续爬和分布式；③SADD 一条命令原子完成查+记，无竞态。再补一句权衡：小规模用 PG 唯一约束也能做（我就实现过 PG 版），Redis 的优势在高频和分布式场景——答出"知道边界"比"吹 Redis"加分。

**Q：scrapy-redis 了解吗？**
要点：它是把 Scrapy 的调度器和去重过滤器搬到 Redis 的库，核心就是本项目手写的这套（指纹 SET + SADD）；它的 Lpush 调度队列用 Redis LIST 实现，可多机共享请求队列。答"我手写了它的去重核心，调度队列部分用 LIST 同理可扩展"即可。

## 七、延伸（下一步可以学）

- LIST 当任务队列：`LPUSH` 进队 + `BRPOP` 出队（阻塞式弹出，消费者没任务时挂起不空转）
- 布隆过滤器（Bloom Filter）：指纹集大到内存吃紧时的降内存方案（有极小误判率，可能"误杀"新 URL，但绝不放过旧 URL）
- 过期时间 `EXPIRE`：验证码、缓存场景的标配
